# Restaurant POS 1.9.24 — explicit printer routing and atomic stock cards

A missing/offline till previously triggered discovery and could silently route payment receipts to a kitchen printer after a delay. Payment jobs now use only the operator-assigned destination. Missing destinations remain visible as failed/retry jobs; assigning the correct role lets pending role jobs retry there without duplicating completed jobs. Explicit test targets remain exact. Station jobs follow address changes only for their own named station.

One saved physical printer can serve receipt, kitchen and warehouse purposes. Kitchen printing supports all dishes or selected dishes (e.g. a till also printing dönər tickets). Station metadata and role destinations commit in one native settings transaction. Failed reads/writes retain the previous setup, edits preserve newer dish mappings, and legacy menu edits cannot erase separately assigned roles. Startup repairs only positively identified, unconfirmed kitchen fallback assignments, retaining intentional sharing.

Catalog product saves now create/link the zero-balance stock card and default one-unit recipe in the same native transaction. The former renderer follow-up swallowed errors and needed separate stock/recipe permissions. Existing real recipes, quantities, costs and inactive cards are retained. Migration 064 repairs historical missing links/cards without inventing stock. Warehouse-to-menu publication reuses the exact existing card for both piece and weighed goods; barcode conflicts roll the entire new catalog save back. Mounted stock views refresh after catalog saves and on return.

## Free-form sizes and customer portal

New catalog entries can create 1–24 sizes (any positive centimeter value up to 300, two decimal places), each as its own ordinary product, price, stock identity and recipe. For example: Marqarit pizza · 29 sm and · 31.5 sm. No shared recipe or guessed scaling is applied. All sizes are committed atomically; duplicate/invalid sizes fail the batch, and replaying the same operation cannot create a second set. Existing variants can be renamed/repriced independently through the ordinary product editor. The former menu item is never silently resized.

The customer workspace adds restaurant-only **Restoran menyusu** and **Kalkulyasiya** views backed by the selected till. The signed RPC allowlists are mirrored in API/native/portal code. Existing customer/device ownership and per-area write checks stay authoritative. Isolated endpoint tests verify unauthenticated, foreign-device, read-only and old-version rejections, plus exact forwarding of the size payload/idempotency key. The till must be on and upgraded to 1.9.24 for menu writes; offline edits retain the existing queued-operation behavior rather than pretending to have applied.

Catalogue scroll tests reach the last of 70 products at 390, 768 and 1366 px. Tested Chromium 151.0.7922.34; actual desktop Electron 43.8.3. Owner browser bundles and bridges use content-addressed names to avoid stale cached editors. Build output is cleaned before reassembly so old hashed chunks cannot be patched twice.

Rebuild the restaurant, then generate portal assets before building the owner app:

```sh
node restoranpos/scripts/assemble-restaurant.mjs
node restoranpos/portal-web/build-warehouse.mjs platform/apps/owner-web/public/warehouse-20261020
npm --prefix platform/apps/owner-web run build
npm --prefix platform/apps/api run build
```

The actual generated owner iframe (browser bridge plus complete shipped renderer) was also booted against isolated owner RPC fixtures. It creates a free-form 29 cm product, passes stable native idempotency keys, refreshes the menu and disables creation in read-only mode. Remote renderer boundaries use parent/API authorization instead of requesting desktop-only billing IPC; the desktop boundary and native/server access guards remain present.
